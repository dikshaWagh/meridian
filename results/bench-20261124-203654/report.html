How to read the numbers

  • e2e: wall-clock time from sending the request until the last byte. This is what a user feels.
  • ttft: time to the first content token on a streamed reply. Prefill and queueing dominate it. It is blank when streaming is off.
  • p95: 95% of successful requests were at or below this value. Use p95, not the mean, for planning.
  • req/s and tok/s: successful requests and completion tokens divided by the measured run duration. These are goodput, so a policy that fails requests does not look fast.
  • fairness CV: coefficient of variation of request counts across healthy replicas of the same model. 0 is perfectly even. token-aware may skew on purpose toward faster replicas.
  • busiest: share handled by the single busiest replica. An even split across N replicas is 100/N%.
  • observed tok/s: client-side completion tokens ÷ generation time (e2e − ttft for streams). Compare it with the server's tok_per_sec to see whether the router had a real speed signal.

Raw data

  • summary.json — machine-readable run summaries
  • summary.csv — one row per policy × concurrency
  • requests.csv — every request with replica, latency and tokens
  • timeseries.csv — status snapshots (in-flight, tok/s, CPU, RAM)
  • replicas.csv — per-replica distribution and speed signal
